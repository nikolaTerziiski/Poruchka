## 0. 🔴 THE PRODUCT BLOCKER — quantities are now editable from Telegram

The audit's §0: the bot had four callbacks (copy, submit, snooze, skip) and **no way to change a
quantity**, while `submitOrder()` blocked when no line had one. Since `defaultQuantity` is optional
and a first reminder has no history to prefill from, the very first reminder a restaurant ever
received dead-ended with *"add quantities in the app"* — telling someone in a walk-in cooler to go
find a laptop.

**Now:** an **✏️ Количества / Quantities** button on every reminder opens an editor that lives
entirely inside the chat.

```
Текст за доставчика | ✏️ Количества | ✓ Изпратена | Напомни след 1 час | Пропусни тази седмица

  ↓ tap ✏️ Количества                    ↓ tap a line

✏️ Количества — Метро                   ✏️ Свинско месо (кг)
• Свинско месо: —                       Сега: —
• Домати: —
                                        = 24
Изберете артикул, за да смените           [1][2][3]
количеството.                             [4][5][6]
                                          [7][8][9]
  [Свинско месо: —]                       [.][0][⌫]
  [Домати: —]                             [Запази] [‹ Назад]
  [Готово]
```

**Design notes**

- **Stateless.** The in-progress entry is rendered into the message as a `= <entry>` line and read
  back on the next tap, so there is no server-side session to lose on restart or across instances.
  Round-tripping is covered by tests, including item names containing `=` or digits.
- **Callback-data safe.** Telegram caps callback data at 64 bytes, so two UUIDs don't fit. Lines are
  addressed by index into a deterministic `(sortOrder, id)` sort — `sortOrder` defaults to `0` and
  is *not* unique, so sorting by it alone would be ambiguous. There's a test for the collision case.
- **Bounds enforced at entry.** The keypad refuses a second decimal point, leading-zero runs, a 7th
  whole digit (`quantitySchema` max 999999) and a 4th decimal (`Decimal(12,3)`) — invalid values
  can't even be typed, and `quantityFromEntry` re-validates before the write.
- **No more dead ends.** Tapping **Изпратена** or **Текст за доставчика** with nothing filled now
  *opens the editor* instead of showing a refusal toast.
- **Same authorization.** Every editor callback goes through `authorizedRun` and is rejected once
  the order leaves `PENDING`/`ESCALATED`. Both are tested.

**Files:** `bot-copy.ts` (render/parse/`applyKeypadKey`/`quantityFromEntry`),
`telegram.bot.service.ts` (`showQuantityList`, `showQuantityPad`, `handleKeypad`,
`showOrderActions`), `scheduler.service.ts` (button wiring).

## 1. 🔴 CRITICAL — `/dev` account-takeover closed

`DevController` is unauthenticated and could mint a Telegram link code for **any user in any
tenant**, letting an attacker bind their own Telegram to a victim's account.

`apps/api/src/app.module.ts` now registers `DevModule` only when `ENABLE_DEV_ENDPOINTS === "true"`.
Documented in `.env.example` with an explicit warning; default is off.

| unset | Prisma, Channels, Features, Scheduler | **absent** |
| `"false"` | — | **absent** |
| `"true"` | Prisma, Channels, **Dev**, Features, Scheduler | present |

## 2. 🔴 The "I already marked it Done" race

**Was:** `dispatch()` read a run, sent the Telegram message, then *unconditionally* wrote
`status`/`nextNudgeAt`/`sentCount`. A user tapping **Sent** during the send window had their
`SUBMITTED` overwritten back to `PENDING` — the completed order was resurrected and kept nagging.
Snoozes were discarded the same way (`postponedUntil: null`).

**Now:** an **atomic claim** advances the row *before* sending, conditional on it still being in the
same state and still due:

```ts
const claim = await this.prisma.orderRun.updateMany({
  where: { id: run.id, status: run.status, nextNudgeAt: { lte: now } },
  data: { sentCount, lastSentAt: now, status: escalated ? "ESCALATED" : "PENDING", nextNudgeAt },
});
if (claim.count === 0) continue;   // user won the race — do not send
```

If the user tapped Sent/Snooze first, the claim matches 0 rows and **nothing is sent**. A crash
mid-dispatch now leaves the row already advanced, so it retries at the next interval instead of
re-sending immediately. The quiet-hours defer is guarded the same way.

Covered by two tests, including one that asserts no send occurs when the claim returns `count: 0`.

## 3. 🟠 Unlinked assignee no longer loops forever

**Was:** an assignee with no `chatUserId` got `nextNudgeAt` pushed forward **without incrementing
`sentCount`**, so `sentCount >= maxNudges` was never reached. A staff member who never linked
Telegram meant the order retried hourly forever and **nobody was ever alerted**.

**Now:** the claim advances `sentCount` regardless of deliverability, so an unlinked assignee
escalates on schedule and the escalation contact is notified.

---

## 4. 🟠 Escalation no longer dead-ends

**Was:** on escalation the run got `nextNudgeAt: null` and one message fired. If that person was
busy, the system went silent permanently.

**Now:** `dispatch()` selects `status: { in: ["PENDING", "ESCALATED"] }`, so an escalated run keeps
resurfacing to the escalation contact at the re-nudge interval until it's actually handled. The
assignee reminder is not re-sent once escalated — only the escalation notice repeats.

---

## 5. 🟠 Downtime no longer drops reminders permanently

**Was:** `materializeToday()` materialized only `[today, today]`. A day of downtime meant those
`OrderRun` rows were never created — the reminders were *gone*, not delayed.

**Now:** each tick materializes `today-3 … today`. The existing `@@unique([orderRuleId, dueDate])`
plus upsert keeps it idempotent, so backfill is free when nothing is missing.

---

## 6. 🟠 Snooze no longer defeats escalation

**Was:** both snooze paths did `sentCount: run.status === "ESCALATED" ? 0 : run.sentCount`, so
snoozing an escalated order zeroed the counter — it could be snoozed indefinitely and never stay
escalated.

**Now:** `sentCount` is preserved on snooze in **both** `order-runs.controller.ts` and
`telegram.bot.service.ts`.

## 7. 🔴 Undo / reopen — new capability

There was **no** reopen, unskip, or undo anywhere; status transitions were strictly one-way. A
mis-tap on "Изпратена" or "Пропусни" permanently falsified the order while the system reported
success.

- **API:** `POST /order-runs/:id/reopen` — `SUBMITTED`/`SKIPPED` → `PENDING`, clearing
  `submittedAt`/`submittedByUserId`/`skipReason` and re-arming `nextNudgeAt`. Rejects other states
  with 409. `sentCount` is deliberately preserved so a genuinely overdue order re-escalates.
- **Telegram:** an **↩ Отмени / Undo** button now appears on both the confirmation and skip replies,
  with an `order:reopen:` handler behind the same authorization check.
